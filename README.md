# F1 race dashboard

FastF1 supplies race classifications, lap positions, inferred pit exits and weather.
MultiViewer supplies approximate circuit geometry. A Python ingest job stores the
processed data; FastAPI serves a Next.js dashboard. Written race summaries are
intentionally absent from the dashboard and are not generated by the scheduled job.
The old summary tools remain available for manual use.

## Run locally

Use Python 3.11 and Node.js 24 LTS.

```sh
python3.11 -m venv venv
venv/bin/python -m pip install -r backend/requirements-dev.txt
venv/bin/python backend/migrate.py
```

Start the API from `backend/` with `../venv/bin/uvicorn api:app --reload`.
Start the frontend from `frontend/` with `npm ci` and `npm run dev`.
The frontend defaults to `http://localhost:8000`; production builds need
`NEXT_PUBLIC_API_URL` set to the public API origin.

To ingest or refresh completed races:

```sh
venv/bin/python backend/pipeline.py --year 2026
venv/bin/python backend/pipeline.py --year 2026 --round 1
venv/bin/python backend/pipeline.py --year 2026 --round 2 --has-sprint
```

These commands use the network and update the selected database. No model API key
is needed. Empty classifications fail without replacing existing data. Recent or
incomplete races refresh daily, older races weekly. Missing sprint loads use
exponential backoff capped at one week. Legacy rows refresh on the next ingest.
A refresh bypasses the FastF1 session cache to pick up upstream corrections and
skips unused telemetry and race-control downloads.

## Database upgrades

`DATABASE_URL` selects PostgreSQL or SQLite. Without it, development uses
`backend/f1_races.db`. `APP_ENV=production` requires `DATABASE_URL`.

Back up an existing database, then run `python backend/migrate.py` before starting
new application code. Imports never create or modify tables. Startup rejects an
unmigrated/incompatible schema with a migration instruction. Migration 1 adds
awarded points and classification status, refresh state, uniqueness constraints
and lookup indexes. It preserves existing rows and refuses duplicate identities
rather than choosing which data to delete. Migrations are serialized with a
PostgreSQL advisory lock or SQLite write lock.

Standings use **source-awarded points**, so shortened races and source-reported
penalties are retained. Legacy results without points return HTTP 409 until their
season is refreshed; the API never guesses their score. Ties use race finish
countback, then names if every stored finish count is equal. Missing races or
sprints still mean incomplete standings. See `docs/championship-rules.md`.

## Docker and deployment

`docker compose up --build` starts the API and frontend on localhost. It creates a
fresh named volume for the database and runs migrations before starting the API;
it does not import an existing host SQLite file. Stop the service before restoring
any database backup. Cache files use a separate `race-cache` named volume so the non-root user can write them.

The backend and frontend images run without root privileges. Docker excludes
local databases, `.env` files and credential directories. Build the frontend with
its actual public API URL; a missing or malformed production build URL fails immediately. `FRONTEND_URL` controls the API's additional CORS origin.

The Render free-service start command explicitly migrates before launching the API.
For paid deployments, move that migration to a release/pre-deploy step and give
the API a database role without schema-management privileges. GitHub's ingest job
uses an ephemeral hosted runner and requires a reachable database URL in its
`DATABASE_URL` secret. It has no access to a model API key.

The API limits race lists to 500 rows and lap lists to 10,000 rows per request;
`offset`/`limit` support pagination and the frontend follows all pages. GETs are
browser-cacheable for 60 seconds. A bounded per-process IP limiter defaults to
120 requests per minute (`API_REQUESTS_PER_MINUTE`). For multiple workers or a
shared proxy, configure an edge/shared limiter and trusted proxy addresses; do
not trust arbitrary client-supplied forwarding headers.

## Verification

```sh
venv/bin/python -m pytest backend/tests -q
cd frontend
npm run lint
npx tsc --noEmit
npm test
NEXT_PUBLIC_API_URL=http://localhost:8000 npm run build
npm audit
```

Backend tests cover HTTP serialization, CORS, rate limiting, migration safety,
refresh policies and ingestion rollback. Set `TEST_POSTGRES_URL` to a disposable
PostgreSQL database to also test migration and re-ingestion against PostgreSQL.
That test creates an isolated schema and removes it afterwards; CI supplies a
PostgreSQL 16 service automatically. Frontend tests cover transport pagination,
independent section errors and cancellation of stale race requests.

The minimatch override in `frontend/package.json` supplies the patched major
version to the TypeScript ESLint dependency; lint is checked against this override.

Backend dependency inputs are `backend/requirements.in` and
`backend/requirements-dev.in`. The generated `.txt` files lock the complete trees
with hashes. Regenerate them after editing the inputs:

```sh
uv pip compile backend/requirements.in --python-version 3.11 --universal --generate-hashes --output-file backend/requirements.txt
uv pip compile backend/requirements-dev.in --python-version 3.11 --universal --generate-hashes --output-file backend/requirements-dev.txt
```

CI runs dependency audits for the frontend and locked backend runtime.
